# Deviations from the pre-registration

## D1 (3 October 2026, while E2 was running): cost bounds for very large colour classes

**What changed.** Two changes in `src/proposed_algorithm.py`:

1. C3 (`_eliminate_small_class`) now checks `len(class) - changed > remaining budget` before counting the unchanged members of a candidate class. Because at most `changed` members can already be recoloured in the current update, the exact count is always larger than the remaining budget in that case, so the loop stops exactly where it stopped before. This is a pure speed-up with identical decisions.
2. C4 (`_plan`) no longer computes a migration plan when the class to be removed has more than `R x max_stall` vertices (300 for R = 3). Emptying such a class would take more than `max_stall` updates even if every recolouring went to the migration, and computing the plan with TabuCol cost minutes on graphs with 10^4 or more vertices, so the rule caps the planning cost. A skipped plan counts as a failed planning attempt (same back-off). *(Corrected 4 October 2026, see D6. This item first said that such a plan would be abandoned for stalling before it could be completed. That does not follow from the stall rule, which drops a plan only after `max_stall` updates without progress, so a plan that keeps making progress is never abandoned. The rule is a cost cap.)*

**Why.** The executed test T23 (a sparse graph with 20,000 vertices) showed a mean update time of 2.9 ms, caused by these two steps scanning colour classes with thousands of vertices. Without the change, E5 (up to 10^6 vertices) could not have run.

**Effect on results already produced.** None, for four independent reasons.

1. *E2 used the pre-registered code.* The E2 worker processes were started at 15:10:12 UTC and had loaded `proposed_algorithm.py` before the change was saved (15:13:30 UTC); Python does not reload a module that is already imported. None of the 770 stored E2 KERB result files contains the `plans_skipped` counter that the change introduced (`results/summary/deviation_D1_check.csv`, column `run_has_plans_skipped_counter`), which confirms that every E2 run executed the code whose hash is recorded in `results/raw/preregistration.json`.
2. *The new rule could not have fired in E2.* Change 2 can only apply when the smallest colour class has more than 100R vertices. The smallest class has at most n/k_t vertices, and over all 770 E2 KERB runs the largest value of n / min_t k_t is 80.1 (homer, n = 561, min_t k_t = 7), below 100, the limit for R = 1 (`deviation_D1_check.csv`, written by `experiments/analyse_results.py`).
3. *Re-running gives identical traces.* `experiments/check_deviation_equivalence.py` re-ran five completed E2 runs with the new code (DSJC250.5 R=3, DSJC500.1 R=10, DSJR500.1 R=25, flat300_28_0 R=1, DSJR500.1 without migration) and found identical per-update colour, recolouring and repair traces in all five.
4. *The diagnostic runs of D5 reproduced E2 with the new code* (added 4 October 2026, see D6). `experiments/fallback_overhead.py`, which ran with the code that contains this change, repeated 700 of the 770 E2 KERB runs (all except those of KERB-tabu) with the same inputs, parameters and seeds. Every repeated run reproduced the stored mean, maximum and final colour counts, total and maximum recolouring, conflict and new-colour rates, number of eliminations and KERB's internal counters exactly (`results/summary/fallback_overhead.csv`, column `differences`, empty for every run).

E3 and E5 were run with the new code.

## D2 (3 October 2026, after all evaluation runs): one added test, documentation corrections and output-format corrections

**What changed.**

1. A designed test case T24 (`experiments/test_case_table.py`) and a matching pytest test (`tests/test_algorithm.py::test_planned_migration_removes_a_class_over_several_updates`) were added. No earlier test isolated the planned migration (C4); the new case checks that, with R = 1, C4 and C3 together remove a three-vertex class over several updates while C3 alone cannot: the plan of C4 moved two of the vertices in the second and third updates, C3 moved the last one in the fourth, which emptied the class, no update recoloured more than one vertex, and without C4 the graph still had three colours after six updates. *(Corrected 4 October 2026, see D6; this item first said "over three updates". Corrected again 5 October 2026, see D6 item 8; the item said that C4 alone removed the class.)* The pytest suite now has 79 tests (previously 78), and the test-case table has 24 cases (previously 23). Both were re-run and all pass (`results/summary/pytest_summary.json`, `results/summary/test_cases.csv`).
2. Module docstrings in four files of `src/` were corrected. Two referred to the wrong report chapter ("Section 6" and "Chapter 10"; now "Chapter 6" and "Chapter 9"). Three attributions to published work were stated more precisely than the sources checked for the report support, so they were reworded or removed: the FF-Repair description now cites only Gyarfas and Lehel (1988) for the first-fit rule, the Tabu-WarmStart description no longer names a specific "Method 1" of Hardy, Lewis and Thompson, and the churn workload no longer claims to follow the update protocol of Yuan et al. (2017). One docstring named a function that does not exist (`dsatur_recompute_sample`; now `dsatur_recompute_cost`). For all four files the abstract syntax trees with docstrings removed are identical before and after the edit, so no executable code changed.
3. The summary CSV files in `results/summary/` were written with six significant digits, which rounded counts above one million (for example, 1,536,008 updates were written as 1,536,010 and 3,196,064 edges as 3,196,060). The writer `_save` in `experiments/analyse_results.py` now uses ten significant digits. Only the output format changed, not any computation.
4. Label placement was corrected in three figures drawn by `experiments/plot_results.py`: the budget labels of the trade-off figure, the value labels of the ablation figure, and the missing tick labels on the time axis of the scalability figure. The plotted data did not change.

**Effect on results.** None. No algorithm, baseline, workload or analysis computation changed, and no experiment was re-run. `experiments/analyse_results.py` was run again to regenerate the summaries from the stored raw results, twice. After items 1 and 2, the E1, E2, E4 and E7 summary files were byte-identical to a copy saved earlier the same day (that copy was taken while E3 was still running and before E5, so those files could not be compared with it). After item 3, every numeric field of every summary file agrees with the previous version to within the previous six-digit rounding (largest relative difference below 5 x 10^-6), and the only numbers quoted in the report that changed are nine counts of updates or edges in E5. Only the test counts in the coverage evidence for C12 changed (79 of 79 tests pass). The timing column of T23 differs between executions because it is a wall-clock measurement.

## D3 (4 October 2026, after all evaluation runs): supplementary memory measurement

**What changed.** The script `experiments/memory_check.py` was added. It measures, with Python's `tracemalloc`, the memory allocated for the adjacency sets and for the state of KERB and FF-Repair on random geometric graphs with n = 10,000 and n = 100,000 (the same generator, seed and churn split as E5), before and after 2,000 updates, and the peak during those updates. Output: `results/summary/memory_check.json`.

**Why.** The E5 runs record the resident memory of the worker process, which also contains the interpreter, temporary edge lists and memory retained from earlier tasks in the same process (the resident memory at the start of the runs ranged from 86 MB to 586 MB). That measure cannot show how much memory each data structure needs, which the report discusses.

**A discrepancy found at the same time.** `docs/preregistration.md` lists the *peak* resident memory as an E5 measurement, but the runner records the resident memory at the *end* of each run (psutil's current RSS), which is not necessarily the peak. The report therefore describes the E5 memory figures as end-of-run values.

**Effect on results.** None on the pre-registered results. The measurement is reported separately and labelled as supplementary.

## D4 (4 October 2026, after all evaluation runs): descriptive statistics of the real streams

**What changed.** The script `experiments/stream_stats.py` was added. For each of the seven real interaction files it computes the number of interactions, the time span from the first to the last time stamp and the number of edge updates per day of the derived sliding-window stream (the update counts are read from the stored E3 and E5 summaries). Output: `results/summary/stream_stats.json`.

**Why.** The problem chapter of the report describes how often real conflict graphs change, which needs the time span of each dataset; no earlier script recorded it.

**Effect on results.** None. The script runs no algorithm and changes no stored result; it only reads the datasets and the summaries.

## D5 (4 October 2026, after all evaluation runs): diagnostic measurement of wasted fallback work

**What changed.** The script `experiments/fallback_overhead.py` was added. The cost analysis written for the report found that `KERB._tabu_repair` and `KERB._tabu_empty_class` build the input of the budgeted TabuCol fallback (a copy of the colouring, and for `_tabu_empty_class` a scan of the class) before `_tabu_resolve` checks the iteration limit. With the pre-registered `tabu_iters = 0` the fallback never runs, so this work changes nothing, but it takes time whenever the repair search runs out of nodes or a class elimination fails with at least two recolourings left. The script repeats every KERB run of E2 (with the budget sweep E4 and the ablations E7), E3 and E5 in which the fallback is switched off, with the same inputs, parameters, seeds and harness and with unchanged code, and times every call of the two methods. KERB-tabu, the ablation with the fallback switched on, is excluded, because there the fallback does real work. Output: `results/summary/fallback_overhead.csv` and `fallback_overhead.json`; log: `results/raw/fallback_overhead_log.txt`.

**Why.** To quantify how much of KERB's measured update time is spent on this wasted work, without changing the code that produced the results. Correcting the code (checking the iteration limit before making the copy) would have made the evaluated code differ from the code in the repository and the report, so the code was left unchanged and the correction is listed as future work.

**Effect on results.** None on the stored results. Every repeated run reproduced the stored colours, recolouring counts and KERB's internal counters exactly (the script records any difference, and the report's value script stops with an error if one is found). The update times reported for KERB include the wasted work; the report gives its share of the time per workload and the change of the mean, median and 95th percentile when it is removed (Results chapter and Appendix B).

## D6 (4 and 5 October 2026, after all evaluation runs): corrections found by the audits of the report

**What changed.** The audits of the report found wording errors in some outputs, comments and docstrings and in this file. They were corrected:

1. `experiments/analyse_results.py` labelled the method of each Wilcoxon signed-rank test by a rule of its own that did not match what SciPy's default (`method="auto"`) does. For the secondary tests S1 and S2 the label was "exhaustive permutation (ties or zeros)", whereas SciPy had used the normal approximation after discarding one zero difference. The script now names the method SciPy actually used, found by comparing the p-value with the exact p-value, and states how many zero differences were discarded; the label of S1 and S2 is now "normal approximation (1 zero difference discarded)". The p-values were always SciPy's own and did not change.
2. The coverage evidence for C1 (valid colouring after every update), written by the same script, gave the experiments of the 845 validated KERB runs as "E2, E3". The count also includes the E4 and E7 runs, and the label now reads "E2, E3, E4, E7". The count did not change.
3. The legend of the repair-steps figure (`experiments/plot_results.py`) called one step "Move into the conflict's class". The counter it shows records moves into the class that C4 is removing, and the label now reads "Move into the class being removed (C4)".
4. A comment in `experiments/config.py` described the 95% coverage target as named in the project brief. It is the project's own target and is not part of the assessment brief.
5. The comment beside the D1 rule in `src/proposed_algorithm.py` repeated the rationale corrected in D1 item 2 above. It now describes the rule as a cost cap.
6. The docstring of `smallest_last_order` in `src/static_coloring.py` gave its cost as O(n + m). With the deterministic tie-break the function uses (the smallest vertex of the lowest non-empty bucket), each step scans a bucket, so the bound is O(n^2 + m).
7. In this file, D1 item 2 (the rationale of the rule) and D2 item 1 (the outcome of T24) were corrected, and D1 item 4 was added. Each change is marked where it was made.
8. *(Added 5 October 2026, after a repeat audit.)* The docstring of `_kempe_chain` in `src/proposed_algorithm.py`, used only by the repair variant KERB-kempe of E7, described the chain as the component of w in the subgraph induced by colours a and b. During a repair, w and the other endpoint of the conflict both have colour a and are adjacent, so that subgraph would contain the conflicting edge. The function follows only edges that join colour a to colour b, and the docstring now says so. In this file, D2 item 1 was corrected again: in T24 the plan of C4 moved two vertices of the class and C3 moved the last one.

**Effect on results.** None. No algorithm, baseline, workload, parameter or analysis computation changed, and no experiment was re-run. For both files in `src/`, the abstract syntax trees with docstrings removed are identical before and after the edit (comments are not part of the tree), and the 79 pytest tests pass; this was checked again after item 8. `experiments/analyse_results.py` was run again on the stored raw results: compared with the previous summaries, only the two method labels in `e2_tests.csv`, the evidence label of C1 in `coverage.csv` and the timestamp and test durations in `pytest_junit.xml` changed, and every number is identical. Of the figures, only the repair-steps figure changed (its legend).
